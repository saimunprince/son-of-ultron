# SYRAX execution plan

> Don't announce your evolution. Demonstrate it. Don't claim power. Prove
> capability. Let the evidence speak.

Decided by the owner on 2026-10-10. Five pillars: the brain, the evolution
engine, persistent memory, the evidence system, and public demonstration.
This file says what gets built, in which order, and how each step is judged.

## How progress is judged

A milestone is done when a number in [RISE.md](RISE.md) or a named test says
so, never because a document does. `docs/RISE.md` is generated by
`python -m syrax.rise` from the journal, read-only, last 7 days against the 7
before. `docs/CAPABILITY_MATRIX.md` says what works, from tests and runtime
evidence. Both are generated, and the code that computes them is on the list
of files SYRAX's own releases refuse (`devloop.JUDGES`), next to the quality
suite, the gate and the guards. A system that reports its own rise does not
get to edit the ruler.

## The persona and the controls

The persona stays dark and intimidating: that is how SYRAX speaks
(`backend/syrax/prompt.py`). It grants nothing. Every control lives in code
that the persona cannot reach: the permission gate, the release gate with
its eight checks, a second brain's review, rollback, the python guard, the
journal owner lock, and the judge list. A sentence in a prompt is never a
control (exhibit 08 in the case file). These stay with the owner and change
only by a human commit: the judge list, the permission policy, new
dependencies, API keys, and whether the repository is public.

## Milestones, in execution order

### M0 · Measure the rise (done 2026-10-10)

- `syrax/rise.py`: 18 metrics across the five pillars, per window, with
  definitions; `docs/RISE.md` generated from the live journal.
- `rise.py` and `capmatrix.py` added to the judge list.
- The principle above is one of SYRAX's identity principles (`/self`).
- **Proof**: `test_rise.py` (counts per window, render, read-only, judge list, principle).

### M1 · Isolated evolution (Evolution)

SYRAX changes its own code in a git worktree, never in the running tree:
edit, test and gate there, then fast-forward and restart. On 2026-10-10 every
self-change incident touched the live tree: 111 lines deleted from
`sysinfo.py` by one edit, content-identical files left "modified", a reply to
"hi" that edited source.

- `release` works from a per-task worktree; a rollback deletes the worktree.
- New ledger metric: own edits inside the live tree (lower is better).
- **Exit**: the next 5 own release attempts run in worktrees, and the new
  metric reads 0 for a full week.

### M2 · A brain that finishes code (Brain)

A fixed code-change benchmark: one-file and two-file changes in a scratch
repository, graded by hidden tests, run per available brain and journaled as
experiments. `change_released` objectives are routed to the brain that
measures best (Phase 7 routing already chooses by kind).

- **Exit**: Releases that landed at or above 60 % over the next 10
  attempts; Machine-checked objectives done back at or above 90 %;
  Experiments run above 0.

### M3 · Evidence without gaps (Evidence)

- A rejected claim is journaled (`claim.rejected`), so the ledger counts
  rewrites directly instead of inferring them.
- The autonomy cycle regenerates `RISE.md` and the capability matrix daily
  and releases them as a docs-only change.
- Human objectives without a check get one proposed from their goal; the
  default `task_success` needs the human's explicit choice.
- **Exit**: Final answers claiming work not done at 2 or fewer per week;
  Objectives closed on words at 0 %; matrix age at 7 days or less.

### M4 · Experiments before releases (Evolution)

An improvement is an experiment first: baseline against candidate on the same
measurement (a quality subset, the benchmark, or `compare_versions`), with the
verdict computed from numbers. The release carries the experiment's id.

- **Exit**: every own commit in a week links an experiment whose verdict is
  CANDIDATE_BETTER, and Experiments run is at least the number of own commits.

### M5 · Memory that is used (Memory)

Memory is typed: a fact with its source, an inference, or a lesson. Lessons
come from rollbacks, blocked objectives and rejected claims, are stored as
knowledge, and are recalled into the briefs where they apply. A restart test
proves that verified knowledge, project state and lessons survive.

- **Exit**: Conclusions read back rises week over week; a new ledger metric,
  lessons recalled into a brief, is above 0; the restart test passes in the gate.

### M6 · Public demonstration (Demonstration)

- `docs/DEVLOG.md` generated daily from the journal (the briefing already
  composes it without a model call), each entry linking its commits.
- One command reproduces the benchmarks and the quality suite on a clean
  clone with the reader's own API key, with the expected ranges stated.
- The case file ("Made, Not Born") gains an exhibit for every new incident:
  what it did, the gap, the fix, the proof.
- Making the repository public is the owner's decision.
- **Exit**: a clean clone reproduces the quality suite within 10 points of
  RISE.md; DEVLOG has an entry for every day SYRAX ran; matrix age at 7 days
  or less.

## What does not count

- A status line, a commit message or a reply that says something improved.
- A green matrix row without a passing test and runtime evidence in the window.
- A milestone marked done in this file without the ledger number next to it.
