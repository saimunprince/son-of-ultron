   well-specified change.** `d9e60cf` (2026-10-03, docs-only), `e2f5c27`
   (2026-10-10: an nvidia-smi GPU probe with its own test; gate #3 GREEN,
   objective 95 closed on `change_released`) and `32b9956` (2026-10-10: the
   Windows CIM fallback, so `system_info` now prints "GPU: AMD Radeon(TM)
   Graphics, 512 MB" on this machine; gate #4 GREEN on all 8 gates, reviewed
   by a second brain, objective 109 closed on the commit). Between them the
   free brains (Gemini flash-lite, Upstage Solar) failed six attempts at that
   fallback: chunked re-reading, the same view five times, 111 lines deleted
   by one `str_replace`, and a finished, tested change ended without
   `release`. What landed it: the kept diff of the attempt whose tests had
   passed, re-applied under the new safeguards. Three commits are a start of
   a track record, not autonomy on hard changes.

   are `python_execute` operations (a third on 2026-10-10, from the freeze fixed
   in `8f4ce75`); a crash mid-python leaves a human to decide.
3. **`python_execute` write scope is unchecked** (paths live inside code); the
   new permission gate refuses destruction for autonomous work and asks a human
   for unnamed targets, but cannot see where a write lands.
4. **Free-tier brains**: 171 failovers in the journal; Gemini free quota is
   ~20 requests per model per day; quality depends on which brain answers.
   On 2026-10-10 they could not finish a two-file code change in 30 steps,
   echoed SYRAX's own step prompt as a final answer three times, and claimed
   "addressed through code optimization" for `release` objectives with no change.
5. **One frontend unit test file**; the UI is exercised by `tsc`, `eslint`,
   `next build` and the bridge tests, not by component tests.
6. **Another tool's worktrees**: Kilo now keeps
   `~/.local/share/kilo/worktree-pool/son-of-ultron-*/copper-bracket` (at `fc561d6`);
   the earlier `.kilo/worktrees/spice-melon` is gone. Left untouched.
7. **RAM**: the machine ran with < 1 GB free during both sessions; SYRAX skips
   cycles under pressure, by design (885 MB on 2026-10-10). Under that load the
   gate failed twice on tests that pass alone (`test_skillevo`, `test_skills`).

### Phase 3: repo_map and apply_patch

- Two tools in `backend/syrax/selfedit.py`. `repo_map` (READ_ONLY) renders the
  system map's components with code, tests and limitations, plus an index of
  the backend modules (lines, first docstring line, own test file), filtered by
  a query; it names the protected set. `apply_patch` (WRITE) applies a unified
  diff with `git apply` to the task's tree (its worktree when isolated), whole
  or not at all; compiles the touched Python; runs the covering tests (the
  system map's component tests plus each module's own `test_<module>.py`,
  bounded, with the gate's test settings) and reports pass or fail. A failing
  test leaves the patch in place for a fix forward; the release gate still
  decides.
- The core journals one `code.changed` per patched file, so the release owns
  exactly those files (`devloop.EDITOR_TOOLS`); `permissions.classify` makes
  the diff's paths the targets, so own work is refused patching a judge at the
  call. The console prompt says: `repo_map`, then `apply_patch`, then
  `release`; judges are left to the human.
- Tests (`test_selfedit.py`): the map; diff paths; apply + compile + covering
  tests pass; a failing test reported with the patch kept; stale, empty,
  non-diff, escaping and non-compiling patches refused whole; a new file with
  no test says so; the release ownership and the journal payloads; the
  permission refusal of a judge; the tools in the toolset and the self-model.

### Phase 1: the protected judge

- The protected set is `devloop.JUDGES` (29 paths): the quality cases, the
  release gate and its definition (`devloop.py`), the guard, the permissions,
  the journal and its owner lock, the benches, the ledger, the matrix and the
  probes.
- Before: `judge_problems` ran only for autonomous and eval tasks, so a release
  in a conversation could commit a change to `quality.py` (a test asserted it).
  Now every SYRAX release that touches the set is refused, in any task kind:
  `refused: backend/syrax/quality.py: this file judges SYRAX's own work; only
  a human changes it`. In a conversation the edit stays in the working tree
  and the refusal tells SYRAX to hand it to the human to review and commit.
- The refusal is journaled as a refusal, not a tool failure: `release` returns
  `release refused: …`, which `agent._refused` flags `refused: true`, and the
  limits and skill-evolution judges skip it.
- At the call, own work (autonomous and eval) is refused writing a protected
  file: `permissions.protected_targets` maps editor paths, worktree paths
  (`.syrax/worktrees/<id>/…`) and code path literals onto the set. Reading a
  judge stays allowed.
- Tests (`backend/syrax/test_protected_set.py`): every path in the set is
  refused in a release (one parametrized case each); a normal change passes;

  worktree and relative path; a judge view is allowed; a normal own edit and
  a human-requested judge edit are allowed; `python_execute` writing
  `guard.py` is refused. `test_devloop.py` now expects the conversation
  release of `quality.py` to be refused (the owner's rule supersedes the old
  "human-approved case change").
