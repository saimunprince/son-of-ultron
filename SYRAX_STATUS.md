### Phase 7: token auth for /ws and /live

- `backend/syrax/auth.py` (a judge): `verdict(origin, allowed, given)`: an
  allowed Origin is trusted as before; a foreign Origin is refused whatever it
  presents; no Origin needs the token (`?token=` or `X-SYRAX-Token`). Applied
  to `/ws`, `/live` and the origin-checked HTTP endpoints (`/stt`, `/tts`,
  `/upload`, the HUD feeds). The token is `backend/config/ws.token` (created
  on first use, 0600, gitignored); `python syrax.py --token` prints it;
  `GET /token` hands it to a page with an allowed Origin only.
- Before: a connection without an Origin header was accepted by both sockets,
  so any local process could drive SYRAX. The UI and the HUD are unchanged
  (their Origin is allowed).
- Tests (`test_auth.py`): token file; the verdict table; sockets without
  Origin refused (1008) and accepted with the token in the query or header; a

### Phase 5: the archive of variants (DGM-style)

- `archive` table in the journal: one row per release attempt (parent commit,
  head commit when committed, decision, summary, objective, task, experiment),
  written by `devloop.record_experiment` through `archive.record_attempt`; a
  quality run scores every committed variant at its `git_head`
  (`score_archive_sync`), so the score is measured, never asserted.
- `archive.select_parent`: sigmoid of the score around 50 %, divided by the
  variant's children; the newest committed variant while nothing is scored.
  `lineage`, `dead_ends`, `brief` (the running build's score, the best parent,
  this objective's dead ends) feed every `change_released` brief
  (`autonomy.archive_brief`). The daily ledger renders `docs/ARCHIVE.md`;
  `docs/EXPERIMENTS.md` (hand-written) points to it. `archive.py` is a judge.
- Tests (`test_archive.py`): rows, scoring by full or short sha, weights and
  children; selection flips to the sibling once an ancestor has three
  children; lineage and dead ends; a report becomes a row; the brief and its
  gate on the objective kind; the rendered table and lineage.

### Phase 3: repo_map and apply_patch

- Two tools in `backend/syrax/selfedit.py`. `repo_map` (READ_ONLY) renders the
  system map's components with code, tests and limitations, plus an index of
  the backend modules (lines, first docstring line, own test file), filtered by
  a query; it names the protected set. `apply_patch` (WRITE) applies a unified
  diff with `git apply` to the task's tree (its worktree when isolated), whole
  or not at all; compiles the touched Python; runs the covering tests (the
  system map's component tests plus each module's own `test_<module>.py`,
  bounded, with the gate's test settings) and reports pass or fail. A failing
  test leaves the patch in place for a fix forward; the release gate still
  decides.
- The core journals one `code.changed` per patched file, so the release owns
  exactly those files (`devloop.EDITOR_TOOLS`); `permissions.classify` makes
  the diff's paths the targets, so own work is refused patching a judge at the
  call. The console prompt says: `repo_map`, then `apply_patch`, then
  `release`; judges are left to the human.
- Tests (`test_selfedit.py`): the map; diff paths; apply + compile + covering
  tests pass; a failing test reported with the patch kept; stale, empty,
  non-diff, escaping and non-compiling patches refused whole; a new file with
  no test says so; the release ownership and the journal payloads; the
  permission refusal of a judge; the tools in the toolset and the self-model.
